# 내구 실행(Durable Execution) — 장애가 섞인 환경에서 에이전트 워크플로우가 무엇을 잃는가

> 측정일 2026-08-18 · 재현: `python tools/bench_durability.py` · `python tools/bench_crash_resume.py` ·
> `python tools/bench_checkpoint_cost.py` · 테스트 `python -m pytest` (133 passed)

---

## ① 왜 했나

이 레포의 `Supervisor`는 단계 결과를 **메모리에만** 둔다. 그래서 세 가지가 없다.

1. **상태 저장이 없다** — 프로세스가 죽으면(OOM 킬·배포 중 컨테이너 교체·SIGKILL) 이미 끝난 단계까지 전부 잃는다.
2. **재시도가 없다** — LLM 429나 네트워크 순단 같은 일시 고장이 그대로 영구 실패로 굳는다.
3. **멱등성이 없다** — 그래서 "실패하면 다시 돌리자"는 순진한 해법이 **되돌릴 수 없는 부작용(검사 성적서 발행)을 중복 실행**한다.

"없다"를 고치기 전에 **없어서 무엇이 얼마나 깨지는지부터 재는 것**이 이 작업의 출발점이다.

## ② 무엇을 만들었나

`app/durable.py` — 체크포인트 · 단계 단위 재시도 · 멱등 부작용을 붙인 `DurableSupervisor`.
`store=None`이면 부모 `Supervisor`와 완전히 같이 동작하므로 **기존 데모·서버 경로는 무영향**이다
(테스트 `test_store_none_matches_plain_supervisor`가 두 답이 같음을 강제한다).

## ③ 설계 결정 4가지와 근거

| 결정 | 대안 | 채택 이유 |
|---|---|---|
| **재개 시 계획을 다시 세우지 않는다** | 재개할 때 라우터 재호출 | 라우터가 다른 경로를 고르면 이미 끝난 단계가 무효가 된다. 계획은 첫 실행에 체크포인트로 박고 그대로 재생 |
| **재시도는 단계 단위** | 요청 전체 재실행 | 성공한 단계를 다시 돌리면 비용도 낭비지만, 부작용을 가진 단계면 **중복 발행**이 난다 |
| **나아지지 않는 실패는 재시도 안 한다** | 전부 재시도 | `no_image`·`unsafe_sql`·`no_llm`은 입력·정책이 원인이라 몇 번을 불러도 같다. `NON_RETRYABLE`로 즉시 확정 |
| **재시도 소진 단계는 사람검토로 승격** | 에이전트의 `needs_human`에 의존 | "재시도 소진"은 **내구 층이 새로 만든 실패 유형**이라 에이전트가 모른다. 만든 층이 책임진다 |

**멱등 키**: 각 단계는 `context["_idempotency_key"] = f"{run_id}:{step}"`를 받는다.
외부로 나가는 액션을 가진 에이전트가 이 키로 중복을 접을 수 있고, 재개 시에는 애초에 그 단계를
다시 실행하지 않으므로 이중 방어다.

## ④ 성능 비교 (실측)

### (a) 고장 주입 200요청 × 4단계 — 같은 고장 스케줄을 세 구성이 공유(짝지음)

고장 모델: 단계마다 일시 고장 25%(1~2회 실패 후 성공) · 영구 고장 3%(재시도해도 실패) · seed 20260818.
`soft`는 에이전트가 예외를 잡아 `ok=False`를 반환하는 경로(vision·analytics의 실제 동작),
`hard`는 예외가 그대로 올라오는 경로(`llm.py`가 429 3회 후 raise).

**soft 고장**

| 구성 | 완주율 | 요청 유실 | 부작용 발행 | **중복 발행** | 재실행 스텝 | 총 호출 |
|---|---:|---:|---:|---:|---:|---:|
| A 현재(재시도 없음) | 25.5% | 0 | 136 | 0 | 0 | 800 |
| B 순진한 재시도(전체 3회) | **85.5%** | 0 | 355 | **161** | 662 | 1,824 |
| **C 내구 실행** | **85.5%** | 0 | 194 | **0** | **0** | **1,162** |

**hard 고장**

| 구성 | 완주율 | **요청 유실** | 총 호출 |
|---|---:|---:|---:|
| A 현재 | 25.5% | **149** | 526 |
| B 순진한 재시도 | 65.0% | 70 | 1,323 |
| **C 내구 실행** | **85.5%** | **0** | 1,162 |

읽는 법 세 가지:

- **B는 완주율을 사기 위해 중복 발행 161건을 지불했다.** 같은 요청에 성적서가 두 장 이상 나간 건수다. 완주율만 보면 B와 C가 같아 보이지만 값이 다르다.
- **C는 B와 같은 완주율을 호출 1,824 → 1,162회(36% 적게)로 낸다.** 성공한 단계를 다시 안 돌리기 때문이다(재실행 스텝 662 → 0).
- **C는 고장이 값으로 오든 예외로 오든 같은 결과를 낸다**(soft·hard 모두 85.5%·유실 0). 예외를 결과로 흡수하기 때문이다. A는 예외일 때 149건을 통째로 잃는다.

**완주율 85.5%가 상한인 이유**: 영구 고장 3% × 4단계 → 요청의 약 11.5%는 어떤 재시도로도 못 살린다
(1 − 0.97⁴ = 11.5%, 관측 14.5%는 n=200의 표본 오차 범위). **재시도가 만능이 아니라는 것을 스케줄에 일부러 넣었다.**

### (b) 진짜 프로세스 강제 종료 → 재개

시뮬레이션이 아니다. 자식 프로세스를 띄워 지정 단계에서 `os._exit(137)`로 죽인다 —
`atexit`도 `finally`도 버퍼 flush도 돌지 않는다. 그리고 같은 `run_id`로 새 프로세스를 띄운다.
실행 흔적은 append+fsync하는 작업 원장에 남겨 프로세스가 죽어도 보존된다.

| 죽인 단계 | A 총 실행 단계 | C 총 실행 단계 | A 성적서 고유번호 | C 성적서 고유번호 |
|---|---:|---:|---:|---:|
| vision | 5 | 5 | 1 | 1 |
| analytics | 6 | **5** | 1 | 1 |
| knowledge | 7 | **5** | 1 | 1 |
| **report** | 8 | **5** | **2** ❌ | **1** ✅ |

- **A는 죽는 지점이 뒤일수록 버리는 일이 늘어난다**(5→8단계). C는 어디서 죽든 **5단계로 평평하다** — 계획 4단계 + 죽은 그 단계 1회 재실행.
- **report에서 죽으면 A는 성적서를 2장 발행한다.** 고유 번호가 2개다(재실행마다 새 번호가 매겨지므로).
  C도 report를 다시 실행하지만 **같은 멱등 키**라 하류에서 1장으로 접힌다.

> **이 표의 핵심은 "체크포인트만으로는 exactly-once가 안 된다"는 것이다.**
> 단계 실행 후에 체크포인트를 저장하므로, 실행 도중 죽으면 그 단계는 반드시 다시 돈다(at-least-once).
> 재실행을 안전하게 만드는 것은 체크포인트가 아니라 **안정적인 멱등 키**다.

### (c) 내구성의 값 — 체크포인트 비용 (200요청 × 4단계, 5회 반복, no-op 에이전트)

| 저장소 | 단계당 ms | CV | 무엇을 더 사는가 |
|---|---:|---:|---|
| none (현재) | 0.013 | 4.6% | — |
| memory | 0.066 | 2.4% | 직렬화만 |
| **file (fsync 없음)** | **1.370** | 7.6% | + 원자적 교체 → **프로세스 사망**에 견딤 |
| file (+fsync) | 3.405 | 1.4% | + **머신 전원 손실·커널 패닉**에 견딤 |

**위협 모델을 정하면 비용이 정해진다.** 막으려는 것이 OOM 킬·컨테이너 교체라면 `os.replace`의
원자성만으로 충분하다 — 프로세스가 죽어도 페이지 캐시는 OS가 들고 있다. `fsync`가 추가로 사는 것은
전원 손실뿐이고 대가는 **단계당 1.37ms → 3.41ms**다. `FileCheckpointStore(path, fsync=False)`로 끈다.

> **배수로 말하지 않는 이유**: no-op 워크로드에서 file 저장소는 none 대비 263배지만, 그 비교는
> 무의미하다. 실제 단계는 LLM 호출 한 번에 수백 ms~수 초를 쓰므로 3.4ms는 1% 미만이다.
> **비용은 배수가 아니라 단계당 절대 시간으로 말한다.**

## ⑤ 교체 기록

- **`build_report`의 신뢰 판정을 `needs_human` 플래그 → `needs_human OR not ok`로 교체.**
  (아래 ⑥-1이 이유다.) 같이 종합신뢰도도 고쳤다 — 실패 단계의 `confidence`를 그대로 `min`에 넣으면
  실패했는데 신뢰도가 1.0로 남는 경로 때문에 종합값이 부풀 수 있어, 실패 단계는 0.0으로 집계한다.
- **순진한 재시도(B)를 후보에서 탈락시킨 근거는 완주율이 아니라 중복 발행이다.** B는 완주율에서 C와
  동률(85.5%)이라 지표를 하나만 봤다면 "재시도만 붙이면 된다"로 끝났을 것이다. **부작용을 세는 지표를
  따로 두지 않았으면 못 봤다.**
- **`fsync`는 계층별로 기본값을 다르게 뒀다.** 저장소 클래스(`FileCheckpointStore`)의 기본은 **켬** —
  라이브러리는 안전한 쪽이 기본이어야 한다. 반면 제품 팩토리(`service.get_durable_supervisor`)의 기본은
  **끔**이다. 거기서는 막으려는 것이 프로세스 사망이라고 **위협 모델을 명시적으로 정했기** 때문이다.
  "기본을 무엇으로 둘까"는 성능이 아니라 **누가 위협 모델을 아는가**로 갈렸다.

## ⑥ 에러 대처 기록

1. **실패한 단계가 있는데 "자동 판정 신뢰 가능"이라고 말하는 리포트** (이 작업의 핵심 발견)

   벤치마크를 짜다가 확인차 넣은 판정이 걸렸다. 같은 리포트 안에서
   `findings`는 `"vision: 실패/미완료 — 결과를 신뢰할 수 없음"`인데
   `recommendation`은 `"자동 판정 신뢰 가능: 모든 단계가 임계 이상으로 완료되었다"`였다.
   `build_report`가 신뢰 판정을 `needs_human` 플래그**에서만** 파생했기 때문이다.

   **얼마나 실재하는가를 먼저 확인했다.** 레포의 `ok=False` 반환 지점 6곳을 전부 읽었더니
   **5곳은 `needs_human=True`를 세우고, `vision`의 `no_image` 1곳만 세우지 않는다.**
   즉 오늘 당장 터지는 경로는 하나다. 그런데도 고친 이유는 —
   **리포트의 신뢰 판정이 각 에이전트의 플래그 규율에 의존하는 구조 자체가 결함**이고,
   내가 지금 추가하는 "재시도 소진"이 바로 그 규율을 모르는 새 실패 유형이기 때문이다.
   구조를 고치고(`not ok`를 직접 반영), 내구 층에서도 소진 단계를 사람검토로 승격해 **두 겹으로** 막았다.
   회귀 테스트 3개(`test_reporting.py`)로 못 박았고, 그중 하나는 4가지 ok 조합을 모두 돌며
   **"findings가 실패를 말하는데 recommendation이 신뢰 가능이라 하는 조합은 없다"**를 강제한다.

2. **벤치마크가 결함을 실제보다 크게 잡고 있었다.** 처음 `FlakyAgent`는 실패 시 `needs_human`을
   항상 안 세웠고, 그래서 "실패 149건 전부가 오도 리포트"라는 숫자가 나왔다. 위 ⑥-1에서 실제 코드는
   6곳 중 5곳이 플래그를 세운다는 걸 확인한 뒤, **규율 있는 에이전트를 모델링하는 `--fault-sets-human`
   스위치를 넣어 두 모델을 다 돌리게 고쳤다.** 149는 "고장 경로가 플래그를 잊었을 때의 크기"이지
   "현재 프로덕션에서 나는 건수"가 아니다. 문서에도 그렇게만 쓴다.

3. **체크포인트 비용이 실행마다 2.5~4.7초로 흔들렸다.** 그대로 배수로 쓰면 안 되는 값이라
   (이 레포의 기존 규칙: 표준편차가 평균의 절반을 넘는 지표는 배수 인용 금지) 비용만 떼어
   5회 반복 측정으로 분리했다. CV 1.4~7.6%로 안정되자 **fsync가 비용의 60%**라는 게 드러났고,
   그게 `fsync` 손잡이로 이어졌다. **흔들리는 값을 버린 게 아니라 다시 재서 손잡이를 찾았다.**

4. **at-least-once를 exactly-once로 착각할 뻔했다.** 크래시 스윕 초기 버전은 baseline의 멱등 키
   대체값을 상수로 뒀는데, 그러면 체크포인트가 없는 A도 중복이 0으로 나온다. 실제 발번 로직처럼
   **실행마다 새 번호(pid 기반)**로 바꾸자 report 크래시에서 A의 고유번호가 2개로 드러났다.
   **테스트 하네스가 관대하면 결함이 사라진다.**

## ⑥-b 제품에 배선하기 — 라이브러리로 두면 기능이 아니다

`app/durable.py`만 있으면 "코드는 있는데 제품에는 없는" 상태다. `service.get_durable_supervisor()`와
CLI `--run-id`로 배선했다.

```bash
python cli.py "스크래치 결함 처리 절차 알려줘" --run-id job-42   # 체크포인트를 runs/job-42.json에
python cli.py "스크래치 결함 처리 절차 알려줘" --run-id job-42   # → [재개] 1단계를 건너뛰었습니다
```

팩토리는 `get_supervisor()`와 **같은 레지스트리·라우터**를 쓴다(테스트로 강제). 이 레포에 이미 있던
"측정한 구성과 배포된 구성이 갈리지 않게 한다"는 원칙의 연장이다. `--budget` 초과 시엔 남은 단계를
체크포인트에 두고 멈추고, 재시도를 소진한 단계가 있으면 CLI가 그 사실을 따로 출력한다.

|---|---|---|
| 1 | `Supervisor`·에이전트·리포트 경로 읽고 무엇이 없는지 확정 | 체크포인트·재시도·멱등 모두 없음 확인 |
| 2 | 고치기 전에 **벤치마크부터** 작성(A·B 먼저 측정) | A 완주율 25.5%, B 중복 발행 161 |

## 근거의 선 (과장하지 않기 위해 명시)

- 여기서 만든 것은 **단일 프로세스·순차 실행에 붙인 내구 실행 층**이다. Temporal·Restate 같은
  워크플로우 엔진을 쓴 경험도, 분산 워커·리스 갱신·중복 실행 방지(fencing)를 갖춘 운영도 아니다.
- 동시성은 다루지 않았다. 같은 `run_id`를 두 프로세스가 동시에 잡으면 두 번 실행된다(락 없음).
- 부작용의 멱등성은 **키를 넘겨주는 데까지**다. 실제로 접는 것은 하류 시스템(MES/QMS)의 몫이고,
  이 레포에서는 벤치마크의 원장이 그 역할을 대신했다.
- 고장 확률(25%/3%)은 관측된 실제 분포가 아니라 **선택한 스트레스 조건**이다. 절대 완주율보다
  **같은 조건에서 구성 간 차이**를 보는 값이다.
